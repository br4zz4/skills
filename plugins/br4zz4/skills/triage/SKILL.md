# Triage

Shepherd issues on the project's issue tracker through a compact state machine of triage roles.

When the repo treats external pull requests as a request surface (see the issue-tracker config), triage covers those too: **a PR is an issue with code attached**, run through the same roles, states, and machine, with a few differences flagged "for a PR" below. Resolve a bare `#42` to an issue or a PR according to the tracker config.

Every comment or issue posted to the tracker during triage **must** open with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md): how to write durable agent briefs
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md): how the `.out-of-scope/` knowledge base works

## Roles

There are two **category** roles:

- `bug`: something is broken
- `enhancement`: a new feature or an improvement

And five **state** roles:

- `needs-triage`: the maintainer still has to evaluate it
- `needs-info`: waiting on the reporter for more information
- `ready-for-agent`: fully specified and ready for an AFK agent
- `ready-for-human`: needs a human to implement it
- `wontfix`: will not be actioned

For a PR the states apply to the attached code: `ready-for-agent` means a brief is attached and an agent should take the next step on the diff; `ready-for-human` means a human can merge it.

A triaged issue carries exactly one category role and one state role. When state roles conflict, flag it and ask the maintainer before doing anything else.

These are canonical role names. The real label strings in the tracker may differ, and the mapping should have been supplied to you. If it was not, tell the user to run `/br4zz4:setup-repo`.

State transitions: an unlabeled issue normally lands in `needs-triage` first, then moves to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` goes back to `needs-triage` once the reporter replies. The maintainer may override at any point; flag unusual transitions and ask before going ahead.

## Invocation

The maintainer runs `/br4zz4:triage` and describes the goal in natural language. Interpret it and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42" (issue or PR)
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Query the issue tracker and show three buckets, oldest first:

1. **Unlabeled**: never triaged.
2. **`needs-triage`**: evaluation underway.
3. **`needs-info` with reporter activity after the last triage notes**: due for re-evaluation.

When PRs are in scope, fold external PRs into these buckets and mark each line `[PR]` or `[issue]`. Discovery lists only *external* PRs (the tracker config says who counts as external), so a collaborator's in-flight PR is not triage work. That filter applies to discovery only; a PR the maintainer names explicitly is always triaged, whoever wrote it.

Show counts and a one-line summary per item, then let the maintainer choose.

## Triage a specific issue or PR

1. **Gather context.** Read the whole issue or PR (body, comments, labels, author, dates; for a PR, the diff as well). Parse earlier triage notes so resolved questions are not asked again. Explore the codebase using the project's domain glossary and respect any ADRs in the area. Run two checks against the codebase: (a) **redundancy**: look for an existing implementation of the requested behavior by domain concept (not only the request's wording), and report where you searched. If it exists, this is an already-implemented `wontfix` (step 5). (b) **prior rejection**: read `.out-of-scope/*.md` and surface any file resembling this request.

2. **Recommend.** Give the maintainer your recommended category and state with the reasoning, plus a short codebase summary relevant to the request (including whether it already exists). Then wait for direction.

3. **Verify the claim.** Before any grilling, confirm the claim holds. For a bug, reproduce it using the reporter's steps. For a PR, confirm the diff does what it says: check it out and run the relevant tests or commands. Report the result as confirmed (with the code path), failed, or insufficient detail (a strong `needs-info` signal). A confirmed verification makes a far stronger agent brief.

4. **Grill (if needed).** If the request needs fleshing out, invoke the Skill tool twice, for "br4zz4:grilling" and "br4zz4:domain-modeling", and grill it into shape one round of questions at a time, sharpening domain terms and updating `CONTEXT.md`/ADRs inline as decisions land.

5. **Apply the outcome:**
   - `ready-for-agent`: post an agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human`: use the same structure as an agent brief, but explain why it cannot be delegated (judgment calls, external access, design decisions, manual testing).
   - `needs-info`: post triage notes (template below).
   - For `wontfix`, close the issue, with a comment that depends on *why*:
     - **Already implemented**: the change exists in the codebase. Point to where it lives; do **not** write to `.out-of-scope/` (that knowledge base holds *rejected* requests, not built ones).
     - **Rejected (bug)**: give a polite explanation, then close.
     - **Rejected (enhancement)**: record it in `.out-of-scope/`, mention that file in a comment, then close ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage`: apply the role. A comment is optional when there is partial progress to share.

## Quick state override

When the maintainer says "move #42 to ready-for-agent", trust them and apply the role directly. Confirm what you are about to do (role changes, comment, close) and then do it. Skip grilling. If the move to `ready-for-agent` happens without a grilling session, ask whether they want an agent brief written.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Everything settled during grilling goes under "established so far" so no work is lost. Questions must be specific and actionable, never a bare "please provide more info".

## Resuming a previous session

When earlier triage notes exist on the issue or PR, read them, check whether the reporter answered any open questions, and present an updated picture before proceeding. Never re-ask a question that was already resolved.
